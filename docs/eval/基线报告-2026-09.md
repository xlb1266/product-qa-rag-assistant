## 4. rerank 分数分布与 0.6 阈值分析

28 条 × 8 个候选 = 224 个 rerank 分数（qwen3-rerank，0~1）：

| 分位数 | 全部候选 | 相关候选（29 个） | 不相关候选（195 个） |
|---|---|---|---|
| min | 0.1425 | 0.4548 | 0.1425 |
| p25 | 0.4027 | 0.8154 | 0.3773 |
| p50（中位） | 0.5262 | **0.8612** | 0.4899 |
| p75 | 0.7029 | 0.9115 | 0.6217 |
| max | 0.9579 | 0.9579 | 0.9313 |

直方图：相关候选 29 个中 **24 个落在 0.8~1.0**，5 个散落在 0.45~0.7；不相关候选 79% 低于 0.6，但也有长尾（最高 0.9313）。

各阈值下的代价（224 个候选汇总）：

| 阈值 | 砍掉相关 | 放过不相关 | 网格实测 recall@4 | 平均保留条数 |
|---|---|---|---|---|
| 0.4 | 0 | 140 | — | — |
| 0.5 | 1 | 93 | **0.9643** | 3.11 |
| **0.6（现状）** | **2** | **57** | 0.9286 | 2.57 |
| 0.7 | 3 | 31 | 0.8929 | 1.93 |
| 0.8 | 5 | 19 | — | — |

**分析**：相关与不相关的分数分布在 0.5~0.8 区间明显交叠（不相关 p75=0.62，相关 p25=0.82 之间没有干净的切点）。0.6 落在交叠区偏右：每查询平均只有 2.57 条过关（top_k=4 经常吃不满），代价是 2/28 的相关候选被误杀；0.5 只多放过约 1.3 条噪音/查询，就能捞回 1 条相关。

## 5. 参数网格（semantic_top_n × rerank_threshold，仅检索层）

| semantic_top_n | RRF recall@8 | RRF MRR | th=0.5 recall@4 | th=0.6 recall@4 | th=0.7 recall@4 |
|---|---|---|---|---|---|
| 5 | 1.0000 | 0.8712 | 0.9643 | 0.9286 | 0.8929 |
| 10（现状） | 1.0000 | 0.8869 | 0.9643 | 0.9286 | 0.8929 |
| 20 | 1.0000 | 0.8869 | 0.9643 | 0.9286 | 0.8929 |

结论：**在当前知识库规模下（41 块主文档 / 全库 1248 块），每路召回 5 条就足以让候选池 100% 覆盖答案**，10 与 20 没有带来任何指标变化。阈值才是唯一敏感参数。

## 6. 结论：参数是否合理，哪些数字值得改

1. **`rerank_threshold=0.6` 偏紧，是当前链路唯一确定的失分点**——回答层 92.86% 的准确率、检索层 0.9286 的 recall@4，全部失败都可归因于它误杀 2 条相关候选（rerank 本身都把期望内容排进了前 2）。建议降到 **0.5**：recall@4 预期 0.9286 → 0.9643，代价是每查询多 ~0.5 条噪音进 prompt（平均保留 2.57 → 3.11 条，仍在 top_k=4 之内）。降档后需在阶段 2 复测防幻觉指标确认噪音无害。
2. **`semantic_top_n=10` 合理**，5 也够用；没有理由调到 20（纯属浪费候选位与 rerank 费用）。
3. **`rerank_top_k=4` 合理**，0.6 阈值下平均只保留 2.57 条、top_k 从未吃满，不构成瓶颈。
4. **rerank 的价值要客观看待**：在这份小而干净的知识库上，RRF 排序本身已 recall@8=1.0，rerank + 阈值反而是净减分（1.0 → 0.9286）。rerank 的真实价值体现在**过滤**——把喂给 LLM 的知识从 4 条压到平均 2.6 条高置信内容，这对阶段 2 的防幻觉是有利面。知识库变大、噪音变多后 rerank 的排序收益才可能显现，届时用同一套脚本重跑即可验证。
5. **a06 暴露的问题属于 chunk 层面**："2.2 添加微信好友"整块只有 43 字，rerank 倾向把提到"微信好友"的长块排前面。这属于阶段 4 chunking 策略要解决的问题（短块与父级标题块的关系），不在本阶段处理。
6. 顺带恢复：调试遗留的 `rerank_top_k=3` 已在评测前恢复为默认 4（config_changes 有留痕，可用调试页回滚）。

## 7. 与后续阶段的衔接

- **阶段 2（防幻觉）**：以本报告第 3 节为基线——回答准确率 92.86%、拒答正确率 100%、误拒率 3.57%。若按第 6 节建议把阈值降到 0.5，改完先重跑本评测确认检索层提升、再复测回答层确认拒答率没被噪音拉低。复跑命令：`cd backend && uv run python eval/run_eval.py`。

## 8. 测试集构建流程（补记）

标准流程为两步，**缺一不可**：

1. **LLM 反向生成问答对**：读知识库文档，每个段落出 2~3 个问法，覆盖三种提问形态——
   直问（按原文直接问）、换词问（口语化改述、同义替换）、多跳问（需要结合上下文才能答）。
   由 LLM 出题保证覆盖面和出题速度。
2. **逐条人工校对**：核对答案确实来自期望段落、关键词确实命中正文（避开标题行与压测文档用词）、
   问法自然。由人工把关保证题目本身没有错——LLM 出的题可能有答案歧义或关键词选错。

人工校对后还需跑 `eval/check_dataset.py` 程序化复核（关键词能否命中某个 chunk、是否撞标题行、
是否在期望文档外误命中）。

**v1 现有 40 条的实际建法（照实记录）**：人工读 `test-data/空气小猪产品知识库.md` 各小节正文出题
（问题均为口语化改述、非原文抄写），逐条人工校对后经 `check_dataset.py` 复核——即 v1 没走
"LLM 反向生成"这步，出题 entirely 人工。将来扩充测试集（阶段 4 chunking 改动后建议扩到 80+ 条）
按上述两步标准流程执行：LLM 反向生成打底提量，人工逐条校对把关。

## 9. 生成段裁判基线（LLM-as-a-Judge）

裁判实现：`backend/eval/judge.py`，复用项目现有 DeepSeek 客户端（`app/core/llm.py`），
json_mode、temperature=0，prompt 内置 0 / 0.5 / 1 分锚点。**裁判上下文取自当次评测的
RetrievalResult**（评的就是生成回答时模型实际看到的那几条 chunk），绝不为裁判重新检索。
只对 answerable 且 useful=true 的回答打分（28 条中 27 条入选，a22 误拒无内容可评）；
unanswerable 不打裁判分，直接算拒答正确率（确定性判定）。

全量裁判结果（2026-09-23，27 条，0 次裁判失败，跑了两轮观察波动）：

| 指标 | 第 1 轮 | 第 2 轮（落盘明细） | 分布（第 2 轮） |
|---|---|---|---|
| **Faithfulness（忠实度）** | 0.9259 | **0.9444** | 24 条 1.0，3 条 0.5，无更低（第 1 轮为 23 条 1.0 / 4 条 0.5） |
| **Answer Relevance（切题度）** | **1.0000** | **1.0000** | 两轮 27 条全部 1.0，当前回答链路没有答非所问 |

忠实度基线取 **0.92~0.94** 区间理解（生成与裁判都有轻微随机性，均值波动 ±0.02）。
两轮共 7 个 0.5 分条目（a06 / a07 / a20 / a24 / a27 / a28，其中 a28 两轮都低），
逐条 reason 已落盘在 `eval-results-2026-09-23.json` 的 `answer_layer.judge_verdicts`，
可直接人工抽查：

| 条目 | 扣分原因（裁判 reason 摘要） | 我们的核查 |
|---|---|---|
| a06 | 核心结论有依据，但"打开 App 找到……"的具体 UI 路径上下文里没有 | 属实：答案补了操作步骤细节 |
| a07 | "你也可……"的补充说法上下文未覆盖 | 属实：轻度夹带 |
| a20 | "方便之后复习"这层目的上下文没提 | 属实：合理推断但非原文 |
| a24 | "其他备考安排"这一因素上下文未提及 | 属实：补充归因 |
| a27 | "随时在设置中切换"的表述比上下文更绝对 | 属实：轻度外推 |
| a28（两轮均低） | "如有调整会另行通知，建议以官方消息为准"上下文没有 | 属实：客服式补充话术，该表述是模型惯性，稳定出现 |

**抽查结论**：7 个 0.5 分判定全部与人工核查一致，且满分答案没有发现该扣未扣的
明显夹带——裁判在本批数据上判定可信。低分条目的共性是**答案夹带了上下文没有的细节**，
属于轻度幻觉（0.5 档），不是编造事实（0.0 档）；这也正是忠实度指标想抓的东西，
说明它能区分"照着上下文说"和"自由发挥"。0.5 分条目随生成波动漂移（除 a28 外
不固定），属正常现象；阈值校准已按"抽样容忍 1 条 0.5 分"设定。

**与关键词指标的分工**：a06 在关键词口径下"回答不正确"（没答到"右上角加号"），
但裁判给了忠实度 1.0（它这次答案完全照上下文说）——两个口径并不矛盾：关键词指标抓
"答没答到要点"，忠实度抓"说的每句是不是有出处"。阶段 2 防幻觉改动看忠实度，
检索/要点层面回归看关键词指标。

### 同源自评局限（必须如实说明）

**裁判与被评模型同源（都是 DeepSeek），存在自评偏袒风险**——同一模型的裁判倾向对自己
惯用的表达风格打高分。缓解手段与残余风险：

- prompt 用了 0 / 0.5 / 1 分锚点强制对标，temperature=0 保证可复现；
- 逐条 reason 落盘，本批已人工抽查确认 4 条扣分属实、满分无漏判（见上表）；
- 残余风险：偏袒可能表现为"对夹带细节更宽容"，实际基线均值可能比真实值略偏高。
  该风险在当前"只看相对变化（改前 vs 改后同一裁判）"的用法下影响有限，
  但**绝对数值不宜与外部论文/其他框架的数字直接比较**。若后续换裁判模型（如与被评模型不同源），
  需重跑一次基线并重新校准 thresholds.json。

## 10. CI 门禁模式

新增两种运行模式（与 v1 的全量 / `--grid` 并存）：

- `--retrieval-only`：只跑检索段确定性指标，**不调任何 LLM**，全量 40 条约 20 秒，
  适合改完 chunking / 检索参数后的频繁回归；
- `--ci`：门禁模式。**检索段全量** + **回答层全量**（answer_accuracy / refusal_accuracy
  需要完整分母）+ **生成段裁判抽样 5 条**（确定性抽样：answerable 按 expected_section
  分组轮转，保证覆盖多章节、每次抽到同样的条目；抽样集当前为 a01/a03/a04/a06/a07）。
  指标逐项对比 `backend/eval/thresholds.json` 下限，**任一跌破 → 退出码 1 并明确列出
  跌破项；全过 → 退出码 0**。已实测验证两种退出码路径均正确。
  另外生成段若出现裁判调用失败，门禁直接视为未通过（不允许"裁判挂了就静默放行"）。

阈值初值（来自基线实测，取整后略降一档留波动空间，依据已写入 thresholds.json 的 notes）：

| 指标 | 基线 | 下限 | 理由 |
|---|---|---|---|
| retrieval.rerank_recall_at_4 | 0.9286 | 0.90 | 28 条中容忍 1 条失分（27/28=0.964 仍过，26/28=0.929 边缘，25/28=0.893 跌破） |
| retrieval.rrf_recall_at_8 | 1.0000 | 0.95 | RRF 融合是候选池上限守护，跌破说明召回源头出问题 |
| retrieval.rerank_mrr | 0.8393 | 0.78 | 略低于基线一档，守排序质量 |
| answer.answer_accuracy | 0.9286 | 0.85 | 2026-09-23 三次全量实测波动 0.8571~0.9286（DeepSeek 生成有随机性），0.85 恰好容纳最差观测；连续贴近下限应排查生成稳定性而非只调阈值 |
| answer.refusal_accuracy | 1.0000 | 0.85 | 8 条中容忍 1 条误拒（0.875 过），2 条跌破 |
| judge.faithfulness | 0.9259 | 0.85 | 5 条抽样中容忍 1 条 0.5 分（均值 0.9 过），2 条 0.5 分即跌破（0.8）；现有 0.5 分答案集中在 a06/a07/a20/a28，抽样含其中 2 条属异常波动 |
| judge.answer_relevance | 1.0000 | 0.85 | 基线满分；跌破说明出现答非所问，值得人工看 |

### 门禁使用方式

```bash
cd backend
uv run python eval/run_eval.py --retrieval-only   # 快回归：改检索参数/chunking 后先跑这个
uv run python eval/run_eval.py --ci               # 完整门禁：提交前/改动收尾跑，看退出码
uv run python eval/run_eval.py --judge            # 全量裁判：手动模式，阶段 2/4 改动收尾跑一次
```

CI 运行明细落盘 `docs/eval/eval-ci-results-<日期>.json`（含门禁逐项判定），
全量裁判明细落盘 `docs/eval/eval-results-<日期>.json`。

  `--retrieval-only` 确认 recall@4 升到 0.9643，再 `--judge` 确认忠实度没被多进来的噪音拉低。
- **阶段 4（chunking）**：测试集绑内容不绑 chunk_id，重新入库后先确认 BM25 索引已重建，

  生成段。若 chunking 改动导致检索指标整体抬升/下降，按新基线重新校准 thresholds.json
  并在 notes 里记录理由。

# 阶段 2 增补（2026-09-23）：回答防幻觉改动前后对比

> 阶段 2 为回答生成环节新增轻量两层防护：①**引用绑定**——回答 prompt 输出格式扩展为
> `{useful, content, citations}`，模型须在 citations 中列出支撑回答的知识条目编号，
> 后端清洗越界/脏编号后随 answer JSON 落库，前端气泡下方展示"引用来源"（可展开知识内容）；
> ②**answerability 预判**——新增代码层拒答（`assess_answerability`，chat.py 与评测脚本共用）：
> 检索为空直接拒答、有真实 rerank 分数且最高分低于新参数 `retrieval.answerability_threshold`
>（默认 0.6）也拒答，命中即不进 LLM，trace 新增 answerability 节点。不做二次一致性校验。

## 12. 拒答阈值定值依据（不凭空拍）

- **探针实测**（40 条测试集全量真实检索）：8 条 unanswerable 题在 `rerank_threshold=0.6`
  下检索结果**全部为空**（4 条 ambiguous 同样为空）——空结果拒答已覆盖全部冷门题；
- answerable 题 top-1 rerank 分数：最低 0.6461、P25 0.8315、中位数 0.8986；
- 因此 `answerability_threshold=0.6`：不误伤任何一条 answerable 题（最低分余量 +0.046）；
  当前与 rerank 过滤下限一致、不重复拦截；若未来按第 6 节建议把 `rerank_threshold` 降到 0.5，
  这道分数字闸门即对 0.5~0.6 区间的低置信结果生效。
