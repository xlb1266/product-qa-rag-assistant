# 阶段 2：回答防幻觉（引用绑定 + answerability 预判）

请在当前 RAG 客服项目中为回答生成环节增加防幻觉机制。

防幻觉要解决的是"让模型自己判断自己有没有依据"的可靠性问题：知识明明按【1】【2】编号喂给了模型，却从不要求它标注引用了哪几条；检索空手或全是低分结果时也照样进 LLM，指望它自觉承认答不了。第一版先做轻量两层防护，满足基本的溯源和拦截需求（已定范围，不扩大）：

- 引用绑定：回答必须标注引用了哪几条检索证据（【编号】），让每个事实可溯源；前端来源展示沿用现有知识库参考面板，不单独新增"引用来源"面板（参考面板已展示全部检索来源，单独面板与其信息重复——2026-09-24 验收决策，原"单独展示面板"要求已撤销，citations 由后端落库供调试页/日志溯源）。
- answerability 预判：检索证据不足时在进 LLM 之前直接拒答，不给模型编造的机会，也省一次调用。

不做二次 LLM 一致性校验（回答生成后再用裁判模型核对答案与证据），避免增加延迟与成本。

引用说明需要明确编号的含义和填写方式，帮助模型正确输出、前端正确消费：

- 回答 prompt 的输出格式扩展为 `{"useful": boolean, "content": "string", "citations": [1, 3]}`：content 中的事实必须来自知识条目，citations 列出支撑回答的条目编号，无引用时为空数组。
- citations 越界（编号超出本次知识条数）或无效要在后端过滤，不得把脏编号透传给前端；模型没返回 citations 或解析失败时按空数组兜底，不得因新增字段导致整体解析失败而走兜底回复。
- citations 随 answer JSON 一起落库；历史消息的 answer JSON 没有该字段，前后端读取一律判空兼容，不迁移旧数据。

拒答的判断要在代码层落实，不能只依靠提示词约束模型：

- 检索结果为空，直接拒答，不进 LLM。
- 检索非空但最高 rerank 分数低于阈值，拒答；阈值进运行时参数（如 `retrieval.answerability_threshold`），默认值参考评测基线报告里的 rerank 分数分布来定，不凭空拍。
- rerank 失败或 mock 降级时没有真实分数，跳过分数判断，只保留空结果拒答。
- 拒答统一使用"暂时不能回答这个问题"这句全系统兜底话术；拦截事件写入链路 trace（新增 answerability 节点，命名遵循 docs/pipeline-nodes.md），让调试页能看到该请求在何处被拦；拒答不进 LLM，但要正常落库、正常返回响应。

改动效果要用评测证明，不能只靠人工感受：用 backend/eval/ 的脚本（含 LLM 裁判）复跑，Faithfulness 应上升（防幻觉改动的直接目标指标），Answer Relevance 不下降（降幅小于 5 个百分点，证明拒答收紧没有误伤正常回答），unanswerable 题的拒答正确率明显上升。结果追加到 docs/eval/ 报告"阶段 2 改动前后对比"一节，并更新 thresholds.json 的 CI 阈值守住新水位。

全部改动需要用 git 管理：每完成一个可独立验证的改动单元（引用绑定 / answerability 预判 / 评测对比）做一次提交，提交信息用中文、说清楚改了什么和为什么；全部完成后 `git status` 工作区必须干净。

完成后先自查上述要求是否逐条满足，再主动询问用户是否手动验收（附建议验收步骤：问一个知识库外的问题确认秒拒且调试页显示未进 LLM、问一个正常问题看知识库参考面板、复跑评测看指标变化），确认通过才算本阶段结束。
