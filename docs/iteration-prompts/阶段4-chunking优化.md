# 阶段 4：Chunking 策略优化

请在当前 RAG 客服项目中优化知识库分块策略。当前 `backend/app/core/chunker.py` 只按 Markdown 标题层级切分：超过 800 字的块按空行段落二次拼接，单段超长按字符硬切（`MAX_CHUNK_CHARS` 模块常量、不可配置）。四个问题：无 overlap 导致切块边界信息丢失、表格/代码块/长列表会被长度规则拦腰截断、800 写死不可调、没有任何实验数据支撑当前策略。本次把切分升级为**结构感知 + 参数可调 + 实验有据**，并用评测数据证明新策略优于现状。

结构感知切分要求（改造 chunker.py，保持 `split_markdown(text, ...) -> list[dict]` 返回结构不变，让调用方零改动或最小改动）：

- **不可切断单元**：Markdown 表格（判定用"连续 ≥2 行、每行以 `|` 包裹且列数一致"，不要用"含 | 的行"这种宽判定误伤正文竖线）、围栏代码块、单个列表项——这些单元作为原子参与拼块，宁可单块超限也不拦腰截断。
- 节内超长时按空行段落聚合（现有逻辑保留），段落间加 **overlap**：从上一块尾部回抄一定字符，保证跨块连续性。
- heading_path 机制不动；硬切兜底保留（不可切断单元自身超长时的最后手段），切点尽量选句号/分号之后。

参数要求：

- `chunking.max_chars`（默认 800，范围 200~2000）与 `chunking.overlap_chars`（默认 0，范围 0~200）进 runtime_config，按 ParamDef 现有写法（key/label/type/default/min/max/分组），调试页热生效；对已上传文档的存量分块不追溯，新参数对新上传文档生效。

存量文档重建要求：

- 注意：数据库不存文档原文，无法直接按文档重切。评估给 documents 表加 `raw_text` 列（走 `database.py` 的 `_MIGRATIONS` 幂等迁移，参考现有写法），让系统自持"按文档重切重建"的能力；重建路径 = 删旧 chunks + FAISS 向量 → 用原文重新分块入库，复用 `process_document_text` 与删除逻辑，保证 chunks / FAISS / BM25 三者一致。若判断加列成本过高，最低限度要在文档里写清"删旧文档重传"的重建操作说明。

评测要求（本阶段核心交付，不可省）：

- 用 `backend/eval/` 的测试集与指标（阶段 1 已就绪；测试集绑定期望内容不绑 chunk_id，切分变了照用）跑新旧策略对比，基线直接引用阶段 1 报告的 Recall@4 / MRR / nDCG。
- 网格实验（max_chars ∈ {400, 800, 1200} × overlap ∈ {0, 50, 100}）用 `--retrieval-only` 模式跑（纯确定性指标、不调 LLM、省钱跑得快）；定稿后用 `--ci` 模式确认新策略不跌破 thresholds.json 阈值。
- 结果落盘 `docs/eval/chunking对比报告.md`：结论必须明确——检索段指标至少不差于基线、表格/列表结构完整性显著更好；若指标回退则回滚策略，不得硬上。
- 成本意识：每次重建文档都要重新调百炼向量化（计费），网格实验控制在 1~3 个文档。

已知约束：

- chunk 自增 id 即 FAISS 向量 ID：重建产生全新 id，旧向量必须删干净（`vector_store.remove`），漏删即脏索引；任何 chunks 变更后必须 `invalidate_bm25_index`。
- overlap 会让相邻块内容重复（特性而非 bug），但 BM25 会因此对同一内容加倍计权，解读评测指标时留意该副作用。
- 若发现测试集命中判定依赖了 chunk 粒度（期望片段恰好是一整块），允许微调 expected_keywords，改动必须记录进对比报告。

Git 提交要求：chunker 结构感知改造、参数接入 runtime_config、存量重建能力、评测对比报告各自独立提交，提交信息用中文、说清楚改了什么和为什么；全部完成后 `git status` 工作区必须干净。

全部完成后先自查上述要求是否逐条满足，再主动询问用户是否手动验收（附建议验收步骤：上传含表格的文档看分块详情确认未被切断、调试页改一次 max_chars 看热生效、查看 chunking 对比报告），确认通过才算本阶段结束——这也是四阶段迭代的收官。
