# 阶段 4：Chunking 策略优化

请在当前 RAG 客服项目中优化知识库的分块策略。

分块决定了检索的基本盘。当前只按 Markdown 标题层级切分：超过 800 字的块按空行段落二次拼接，单段超长按字符硬切，切分长度写死不可调。四个问题：无 overlap 导致切块边界信息丢失；表格、代码块、长列表会被长度规则拦腰截断；参数不可配置；没有任何实验数据支撑当前策略。本次把切分升级为结构感知 + 参数可调 + 实验有据。

结构感知的规则需要明确什么不能切断、如何拼块，让特殊内容保持完整：

- 不可切断单元：Markdown 表格（判定用"连续两行以上、每行以 `|` 包裹且列数一致"，不要用"含 | 的行"这种宽判定，会误伤正文竖线）、围栏代码块、单个列表项——这些单元作为原子参与拼块，宁可单块超限也不拦腰截断。
- 节内超长时按空行段落聚合（现有逻辑保留），相邻块之间加 overlap（从上一块尾部回抄一定字符），保证跨块的连续性。
- 标题层级路径（heading_path）机制不动；硬切保留为不可切断单元自身超长时的最后手段，切点尽量选句号、分号之后。

参数与存量数据的要求：切分长度与 overlap 进运行时参数（如 `chunking.max_chars` 默认 800、`chunking.overlap_chars` 默认 0），按现有参数定义的写法接入，调试页可改、热生效；新参数只对新上传文档生效，存量文档不追溯。注意数据库不存文档原文，无法直接按文档重切——评估给 documents 表加 raw_text 列（走现有幂等迁移机制）让系统自持重建能力；重建路径 = 删旧 chunks 与 FAISS 向量 → 用原文重新分块入库，必须复用现有入库与删除逻辑，保证 chunks / FAISS / BM25 三者一致，漏删向量就是脏索引。若判断加列成本过高，最低限度要在文档里写清"删旧文档重传"的重建操作说明。

改动效果要用评测证明，不能只看表格没被切断就宣布成功：用 backend/eval/ 的测试集与指标跑新旧策略对比（测试集绑定期望内容不绑 chunk_id，切分变了照用），基线直接引用阶段 1 报告的 Recall@4 / MRR / nDCG；网格实验（长度 × overlap 的组合）用 `--retrieval-only` 模式跑，纯确定性指标、不调 LLM；定稿后用 `--ci` 模式确认新策略不跌破 thresholds.json 的阈值。结果落盘 docs/eval/chunking对比报告.md，结论必须明确：检索段指标至少不差于基线、表格/列表结构完整性显著更好；若指标回退则回滚策略，不得硬上。成本上每次重建都要重新调百炼向量化（计费），网格实验控制在 1~3 个文档。overlap 会让相邻块内容重复——这是特性不是 bug，但 BM25 会因此对同一内容加倍计权，解读指标时留意该副作用；若发现测试集命中判定依赖了 chunk 粒度，允许微调期望关键词，改动必须记录进报告。

全部改动需要用 git 管理：分块改造、参数接入、重建能力、评测对比报告各自独立提交，提交信息用中文、说清楚改了什么和为什么；全部完成后 `git status` 工作区必须干净。

完成后先自查上述要求是否逐条满足，再主动询问用户是否手动验收（附建议验收步骤：上传含表格的文档看分块详情确认未被切断、调试页改一次切分长度看热生效、查看 chunking 对比报告），确认通过才算本阶段结束——这也是四阶段迭代的收官。
