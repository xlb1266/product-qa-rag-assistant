## 当前 Chunking 现状（2026-09-22 核实）

`backend/app/core/chunker.py`（全文不到 80 行）：

- 按标题层级切：每遇 `#`~`######` 开新块，块内容 = 标题行 + 该节正文，`heading_path` 记录层级路径
- 超过 `MAX_CHUNK_CHARS = 800` 的块按空行段落二次拼接切分，单段仍超长按字符硬切（`_split_long`）
- **问题**：
  1. 无 overlap，切块边界信息丢失（连续论述被切断后两头都检索不全）
  2. 表格会被空行/长度规则切碎（Markdown 表格行间无空行，但超 800 字照样硬切，表格拦腰截断）
  3. 代码块、长列表同样无保护
  4. 800 这个数字不可配置（模块级常量，不在 runtime_config）
  5. 没有任何实验数据支持当前策略

调用方：`documents.py` 的 `process_document_text`（入库管线，chunk 结构 `{seq, heading_path, content}`）。

## 实现要求

### 1. 结构感知切分（核心）

改造 `chunker.py`（保持 `split_markdown(text, ...) -> list[dict]` 的返回结构不变，调用方零改动或最小改动）：

- **不可切断单元**：Markdown 表格（`|` 连续行块）、围栏代码块（``` 包裹）、单个列表项尽量完整——这些单元作为原子参与拼块，宁可单块超限也不要拦腰截断
- **语义段优先**：节内超长时按空行段落聚合（现有逻辑保留），但段落间加 **overlap**（新参数，默认 0~100 字符量级，从上一块尾部回抄），保证跨块连续性
- **标题路径保留**：heading_path 机制不动
- 硬切兜底仍保留（不可切断单元本身超长时的最后手段），但硬切点尽量选句号/分号后

### 2. 参数进 runtime_config（热生效）

仿照 `runtime_config.py:33-36` 的 ParamDef 增加切分参数（分组"分块"）：

- `chunking.max_chars`（默认 800，范围 200~2000）
- `chunking.overlap_chars`（默认 0，范围 0~200）
- 注意：`split_markdown` 现在是无状态纯函数、常量在模块级——需要让它读运行时配置（`get_runtime()`），或者由 documents.py 调用时传参（推荐后者，保持 chunker 可独立测试）

### 3. 存量文档重建（改了策略必须重建索引）

提供重建方式（二选一，推荐 b）：

- a. 管理端点：`POST /api/documents/{id}/rechunk`——删该文档旧 chunks + FAISS 向量，用文档原文重新分块入库（需要 documents 表存原文或从 chunks 拼不回原文——**注意：当前库不存文档原文！** 所以要引出方案 b）
- b. **重新上传**：文档原文在本地 test-data/ 都有，改完策略删旧文档重传即可；同时评估是否给 documents 表加 `raw_text` 列让系统自持重建能力（加列走 database.py 的 _MIGRATIONS 幂等迁移，参考现有写法）
- 无论哪种，都要保证 chunks 表 / FAISS / BM25 三者一致（复用 `process_document_text` 和删除逻辑就天然一致）

### 4. 用评测证明效果（本阶段的核心交付）

用阶段 1 的测试集与脚本（`backend/eval/`）跑新旧策略对比：

1. 基线：当前策略（纯标题 + 800 硬切）的 Recall@4 / MRR / nDCG（阶段 1 报告里已有，直接引用）
2. 新策略默认参数：同指标
3. 小网格（可选）：max_chars ∈ {400, 800, 1200} × overlap ∈ {0, 50, 100} 的检索段指标对比
4. 网格实验用 `--retrieval-only` 模式跑（纯确定性指标、不调 LLM，省钱跑得快）；定稿后用 `--ci` 模式确认新策略不跌破阶段 1 定的阈值
5. 结果落盘 `docs/eval/chunking对比报告.md`：结论必须明确——新策略好在哪（指标 + 结构完整性两维度，指标至少不差、表格/列表完整性显著更好）

**成本提醒**：每次重建文档都要重新调百炼向量化（计费），网格实验控制文档数量，1~3 个文档足够。

## 坑清单

1. **chunk_id 是 FAISS 的向量 ID**，重建 = 全新的 chunk id，旧 id 的向量必须删干净（`vector_store.remove`），漏删就是脏索引
2. **BM25 索引内存缓存**：任何 chunks 变更后必须 `invalidate_bm25_index()`（复用现有入库/删除路径自带，新写的路径要记得）
3. **阶段 1 测试集绑的是期望内容不是 chunk_id**，所以切分策略变了测试集照用——如果发现测试集命中判定依赖了 chunk 粒度（比如期望片段恰好是一整块），允许微调 expected_keywords，但要在报告里记录改动
4. **表格识别别用"含 | 的行"这么宽的判定**，会误伤正文里的竖线；用"连续 ≥2 行、每行以 | 开头结尾且列数一致"这类规则
5. **overlap 会让相邻块内容重复**——这是特性不是 bug，但 BM25 索引会因此对同一内容加倍计权，观察评测指标时要留意这个副作用
6. **uvicorn --reload 只监控 .py**：改 runtime_config 参数定义后重启后端更稳

## 验收标准

1. 表格、代码块、长列表在分块详情页可见**未被切断**（拿含这些结构的文档验证）
2. `chunking.max_chars` / `chunking.overlap_chars` 在调试页可改、保存后对**新上传文档**生效（存量文档需重建，见实现要求 3）
3. 评测对比报告落盘，新策略检索段指标不差于基线、结构完整性明显更好；`--ci` 模式全过（含更新后的阈值）
4. 重建后 chunks / FAISS / BM25 一致（检索无脏结果、无命中已删块）
5. 原有纯标题 Markdown 文档的 heading_path 展示不受影响
