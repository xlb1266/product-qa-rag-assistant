# 阶段 1：检索效果评测体系升级（LLM 裁判 + CI 门禁）

请在当前 RAG 客服项目中完善检索效果评测体系。评测要回答的问题是"检索链路的参数（每路召回 10、RRF 融合取 8、rerank 后取 4、阈值 0.6）为什么这么设"，并为阶段 2（防幻觉）和阶段 4（chunking）的改动提供可复用的度量衡。整体对齐 RAGAS 等成熟开源评测框架的三个核心：**分阶段评测、用 LLM 当裁判、接入 CI 做门禁**。

注意：评测 v1 已于 2026-09-22 落地——`backend/eval/`（40 条测试集 dataset.json、check_dataset.py、metrics.py、run_eval.py）和 `docs/eval/基线报告-2026-09.md` 均已存在，检索段确定性指标（Recall@K / MRR / nDCG、rerank 前后对比、阈值分布、关键词匹配式回答准确率、拒答正确率）已跑出基线。**本次是增量升级，已有代码、测试集与基线数据直接复用，不推倒重来**，只补 v1 缺的三块：生成段 LLM 裁判、CI 门禁模式、测试集构建流程补记。

评测必须分两段打分，两段的方法论不同，不能混用：

- **检索段（确定性指标，有 Ground Truth 直接算，不调 LLM）**：判断找得全不全、排得准不准。保留 v1 的 Recall@K（K=4/8）、Hit Rate、MRR、nDCG，命中判定基于测试集标注的期望关键词/期望内容（绝不能绑定 chunk_id，阶段 4 改切分策略后 chunk_id 会全部变化）。参数网格实验（如 semantic_top_n、rerank_threshold 扫描）只跑本段指标，一条 LLM 都不调。
- **生成段（LLM-as-a-Judge）**：忠实度、答案相关性这类语义质量，关键词匹配测不了，必须交给裁判 LLM。对 answerable 题的生成回答，把「问题 + 当次检索到的上下文 + 生成的答案」交给裁判，输出 Faithfulness（答案的每个事实陈述是否被上下文支持，防幻觉的核心指标）和 Answer Relevance（答案是否切题）两个 0~1 分值，并逐条给出 reason，便于人工抽查裁判本身靠不靠谱。unanswerable 题不打裁判分，直接算拒答正确率（useful=false 即正确，确定性判定）。

裁判的实现约束：

- 复用项目现有的 DeepSeek 客户端封装（`app/core/llm.py`），json_mode 输出，temperature 设 0；裁判 prompt 要给评分锚点（如 0 分、0.5 分、1 分各举一例），避免打分离散。
- 裁判拿到的上下文必须取自当次评测的 RetrievalResult，不允许为裁判重新检索一次（两次检索结果可能不同，评的就不是同一次回答了）。
- 裁判与被评模型同源（都是 DeepSeek），存在自评偏袒风险，这一局限要如实写进基线报告，不得略去。

测试集构建方式需要补记进报告：LLM 反向生成问答对（读知识库文档，每个段落出 2~3 个问法，覆盖直问/换词问/多跳问）+ 逐条人工校对，两步缺一不可；v1 已有的 40 条是怎么建的照实记录，将来扩充测试集按此流程执行。

CI 门禁模式，让评测能像单元测试一样守住回归：

- 新增阈值配置 `backend/eval/thresholds.json`（如 recall_at_4、mrr、faithfulness、reject_accuracy 各设下限），初值按基线报告结果定并略低于基线留出波动空间，不凭空拍。
- `run_eval.py` 增加 `--retrieval-only`（只跑检索段确定性指标，不调 LLM，快，适合频繁回归）和 `--ci`（指标与阈值对比，任一跌破 → 退出码 1 并明确列出跌破项；全过 → 退出码 0）两种模式。LLM 裁判类指标慢且花钱，门禁默认全量跑检索段 + 抽样跑生成段（如每类抽 5 条），全量生成段走手动模式。
- 指标计算函数保持在独立模块（v1 的 metrics.py），阶段 2/4 都要复用，不要和脚本入口揉在一起。

产出要求：基线报告追加"v2 增补"一节，记录裁判指标基线（Faithfulness / Answer Relevance 均值与分布、拒答正确率）、同源自评局限性说明、CI 阈值初值及理由。业务代码零改动——retrieval.py、answer.py、chat.py 一行都不动，只加评测文件。

执行中的已知约束：

- `debug.mock_third_party=true` 会跳过 embedding 和 rerank，只可用于调脚本骨架，正式跑分必须关闭。
- BM25 索引有内存缓存，评测中途若重新入库过文档，先确认索引已失效重建。
- 评测直接在进程内调用检索与回答函数（async，用 asyncio.run），不要起服务器再发 HTTP 请求。
- Windows 控制台打印中文指标若 GBK 报错，文件头加 `sys.stdout.reconfigure(encoding="utf-8")`。
- 成本意识：每条 query 全量评测 = embedding + rerank + 生成 + 裁判共 4 次计费调用，50 条以内可接受；网格实验严禁调 LLM。

全部完成后先自查上述要求是否逐条满足，再主动询问用户是否手动验收（附建议的验收步骤清单），确认通过才算本阶段结束。
